## Findings

### R3 follow-up — P1: stale-lock reclamation can delete a new owner's live lock

Location: `apps/ops/src/lifecycle-lock.ts:118–119` at the reviewed head.

The token comparison followed by `rmSync()` is a read followed by an unlink, not a conditional atomic removal. Two commands recovering the same abandoned lock can interleave:

1. A reads the stale token in the condition on line 119 and is descheduled before unlinking.
2. B removes that stale file, creates its own lock, and enters its protected operation.
3. A resumes and unlinks the path, which now belongs to B. A's next exclusive create succeeds.
4. A and B both execute their supposedly exclusive callbacks.

The independent reproducer runs the actual lock module in **two real Node processes**. It starts with a valid dead-owner record, pauses A just after that stale-token read, lets B enter `prune`, then resumes A. Both callbacks remain entered simultaneously, with B's live token replaced by A's token. Only scheduling is controlled; the locking algorithm is unchanged. No Docker or database is needed for this proof.

This reopens the original prune-versus-activation hazard after a crash. The existing live-owner tests and L9–L11 do not exercise two concurrent stale-owner reclaimers. The separate import recovery depends on the same global lock.

Required outcome: use an interprocess exclusion mechanism whose ownership cannot be replaced by this read/unlink race. Preserve nested rollback → activate, fail-fast or bounded-wait behavior, fresh installation, crash recovery, and conservative treatment of unknown owners. Merely checking the token again before unlinking has the same gap. Add a deterministic cross-process stale-reclamation regression and verify that at most one protected callback runs.

### R5 — P2: restore combines different generations after an interrupted backup

Location: `apps/ops/src/backup.ts:61–64`; writer ordering at `:23–29`.

`backup` writes SQL, state and manifests one after another into a reusable output directory. `restore` independently selects the newest filename of each kind. If a later backup stops after writing its SQL file, the directory contains a newer SQL dump alongside the previous complete state/manifest archives. Restore accepts this combination and starts replacing the control database.

The reproducer creates an older set with SQL, state and a manifest archive, then adds only the SQL file of a later interrupted backup. The actual restore function replays the newer SQL while applying the older settings/history. It does not report an incomplete or mixed set. Real tar extraction and filesystem operations run; Docker and SQL calls are recorded rather than executed.

Required outcome: publish and select one coherent completed backup generation. Validate the selected set and its required files before any database replacement. An incomplete or corrupted generation must be rejected or explicitly skipped in favor of an identified complete generation; files must never be selected independently across generations. A completion manifest with file hashes written last is one possible design. Include any requested managed sources in that generation's completion/verification contract. Preserve separately restored secrets and the documented secrets → init → restore → re-import → activate order.
